# naf-auth

جسر المصادقة بين منصات ناف وخدمة الهوية المركزية `naf-id`.

**المبدأ:** المصادقة مركزية، والصلاحيات موزّعة. المركز يقرّر الدخول من عدمه، وكل ما بعد الباب تقرّره المنصة من جدولها المحلي.

الحزمة تفعل ثلاثة أشياء لا رابع لها:

1. **الوسيط** — يحمي كل المسارات، ويحوّل غير المسجَّل إلى المركز، ويحقن المستخدم في سياق الطلب
2. **مسار الاستقبال** — يبادل رمز العبور، ينشئ العضو محلياً عند أول دخول، ثم يفتح جلسة المنصة
3. **التحقق** — من التوقيع عبر `JWKS` مع كاش، بلا أي اتصال بقاعدة المركز

**وما لا تفعله:** لا تدير أدواراً، ولا ترسم واجهة، ولا تعرف شيئاً عن منطق المنصة.

**بلا تبعيات خارجية** — التوقيع يُتحقَّق منه عبر `WebCrypto` مباشرة، لأن كل تبعية هنا تُحمَّل على المنصات الخمس.

## الربط في ست خطوات

### ١ — أضف التبعية مثبَّتة على وسم

```json
"dependencies": {
  "naf-auth": "github:fahadaali/naf-auth#v3.0.0"
}
```

**ثبّت على وسم إصدار لا على `main`** — وإلا تغيّر سلوك المنصات الخمس فجأة عند أي تعديل في الحزمة.

**ولا تثبّت على `v1.0.0`.** أسماء حقوله تخالف ما يقرؤه المركز، وكان يولّد
حالةً عابرة لا يعيدها المركز — فكل دخول يفشل بـ`bad_state` قبل أن تقع
المبادلة أصلاً. انظر «الاستقرار والتوافق».

### ٢ — أنشئ مساحة `KV` واربطها

```bash
wrangler kv namespace create AUTH_KV
```

ثم في `wrangler.toml`:

```toml
[[kv_namespaces]]
binding = "AUTH_KV"
id = "<المعرّف العائد من الأمر>"
```

المفاتيح الثلاثة التي تستعملها الحزمة:

| المفتاح | المحتوى | العمر |
|---|---|---|
| `sess:{sid}` | جلسة المنصة | ما بقي من عمر الرمز (١٥ دقيقة على أكثر تقدير) |
| `jwks:{issuer}` | كاش المفاتيح العامة | ٥ دقائق |

ولا مفتاح حالة عابرة: `state` يولّده المركز ويخزّنه مع رمز العبور، ويطابق
الاثنين عند المبادلة. وهذا الطرف يعيده كما وصله.

### ٣ — أنشئ جدول الأعضاء

**منصة جديدة بلا مستخدمين سابقين:** انسخ `migrations/members.sql` إلى مجلّد هجرات المنصة وطبّقه.

```bash
wrangler d1 migrations apply <اسم القاعدة> --remote
```

**منصة لها نظام أعضاء قائم:** لا تنشئ الجدول. الربط هنا يحتاج **خطة ترحيل** تُحلّ `sub` القادم من المركز محلّ المعرّف المحلي في كل الجداول المرتبطة به، ثم تُضبط أسماء جدولك وأعمدتك في الخطوة الرابعة. الهجرات للأمام فقط.

المخطّط الافتراضي:

```sql
CREATE TABLE members (
  user_id      TEXT PRIMARY KEY,   -- sub القادم من المركز
  display_name TEXT,
  email        TEXT,
  role         TEXT NOT NULL DEFAULT 'viewer',
  perms        TEXT,               -- JSON للصلاحيات الدقيقة
  is_active    INTEGER NOT NULL DEFAULT 1,
  last_seen_at INTEGER,
  created_at   INTEGER NOT NULL
);
```

**أول دخول ينشئ السجلّ بالدور الافتراضي.** ثم يرقّيه مسؤول المنصة من إعداداتها، ولا شأن للمركز بذلك إطلاقاً. والدخول الثاني يحدّث الاسم والبريد وآخر ظهور فقط — **ولا يمسّ الدور ولا حالة التفعيل**، وإلا عاد كل مستخدم إلى الدور الافتراضي عند كل دخول وفُكّ إيقاف الموقوف بمجرّد محاولته الدخول.

### ٤ — اضبط `wrangler.toml`

```toml
[vars]
PLATFORM_ID = "naf-marketing"
AUTH_ISSUER = "https://id.naf.sa"
```

**وما يتغيّر بين منصة وأخرى هو `wrangler.toml` وحده.**

والمتغيّرات الاختيارية لا تُكتب إلا إذا خالف مخطّط منصتك الافتراضي. والعمودان الاختياريان يُعطَّلان بالقيمة `-` — لا بقيمة فارغة، فالفراغ في TOML يُقرأ غياباً لا نفياً:

| المتغيّر | الافتراضي | متى يُضبط |
|---|---|---|
| `DEFAULT_ROLE` | `viewer` | إذا كانت للمنصة مفردات أدوار خاصة بها |
| `MEMBERS_TABLE` | `members` | جدول أعضاء قائم باسم آخر |
| `MEMBERS_ID_COLUMN` | `user_id` | عمود المعرّف باسم آخر |
| `MEMBERS_NAME_COLUMN` | `display_name` | |
| `MEMBERS_EMAIL_COLUMN` | `email` | |
| `MEMBERS_ROLE_COLUMN` | `role` | |
| `MEMBERS_PERMS_COLUMN` | `perms` | `-` إن لم يوجد العمود |
| `MEMBERS_ACTIVE_COLUMN` | `is_active` | |
| `MEMBERS_CREATED_COLUMN` | `created_at` | |
| `MEMBERS_LAST_SEEN_COLUMN` | `last_seen_at` | `-` إن لم يوجد العمود |
| `MEMBERS_TIME_FORMAT` | `epoch` | `iso` إذا كانت أوقات المنصة نصّية |
| `AUTH_DB_BINDING` | `DB` | ارتباط `D1` باسم آخر |
| `AUTH_KV_BINDING` | `AUTH_KV` | ارتباط `KV` باسم آخر |
| `AUTH_COOKIE_NAME` | `naf_sid` | |

### ٥ — اضبط السرّ

```bash
wrangler secret put AUTH_CLIENT_SECRET
```

**عبر `wrangler secret` حصراً.** لا يظهر في الكود ولا في `wrangler.toml` ولا في سجلّات الأخطاء ولا في رسالة عرضية للمستخدم.

### ٦ — أضف الملفّين وصفحة الرفض

#### Cloudflare Pages Functions

`functions/_middleware.js`:

```js
import { createConfig, pagesMiddleware } from 'naf-auth';

export const onRequest = (context) => pagesMiddleware(createConfig(context.env))(context);
```

`functions/auth/callback.js`:

```js
import { createConfig, pagesCallback } from 'naf-auth';

export const onRequest = (context) => pagesCallback(createConfig(context.env))(context);
```

ثم تقرأ الصفحات المستخدم من `context.data.user`.

#### Worker على Hono

```js
import { createConfig, handleCallback, honoMiddleware } from 'naf-auth';

app.get('/auth/callback', (c) => handleCallback(c.req.raw, c.env, createConfig(c.env)));
app.use('*', (c, next) => honoMiddleware(createConfig(c.env))(c, next));
```

ثم تقرأ المسارات المستخدم من `c.get('user')`.

#### صفحة `/denied`

تُبنى على سجلّ التصميم `fahadaali/naf-ui`: لا قيمة لون مباشرة، وخصائص اتجاه منطقية لا فيزيائية، وأيقونات `Lucide` بمعانيها المقرّرة في `naf-icons.md`، ونصوص من `naf-terms.md` حصراً، والحالة لا تُبلَّغ باللون وحده.

والحزمة تمرّر **رمز سبب** لا جملة، والصفحة تترجمه إلى المصطلح المسجَّل — فلو حملت الحزمة الجملة لصارت مصدر نصّ ثانياً خارج السجلّ:

| `?r=` | المعنى |
|---|---|
| `inactive` | العضو موقوف من مسؤول المنصة |
| `not_member` | لا سجلّ للعضو في هذه المنصة |
| `bad_state` | وصل رمز عبور بلا حالة تصحبه |
| `auth_failed` | فشل التحقق أو المبادلة |

وما يأتي من المركز نصّاً يُعرض كما هو. **ولا تكشف الصفحة تفاصيل تقنية ولا وجود مستخدمين آخرين.**

## المسارات العامة

قائمة المسارات العامة تُكتب صراحةً، **وأي مسار جديد محمي افتراضياً**:

```js
createConfig(env, {
  publicPaths: ['/auth/callback', '/denied', '/health'],
  publicPrefixes: ['/assets/'],
});
```

والمطابقة بالمساواة التامة أو ببادئة مُعلنة — لا أنماط عامة ولا اجتهاد على الامتداد.

---

## التبليغ العكسي

عند إيقاف عضو من إعدادات المنصة، أبلغ المركز ليظهر السبب للمستخدم في شبكته:

```js
import { createConfig, reportAccessChange } from 'naf-auth';

await reportAccessChange(env, createConfig(env), {
  email: member.email,
  state: 'revoked',
  reason: 'أُوقف من إعدادات المنصة',
});
```

**والعضو يُعرَّف بالبريد لا بمعرّفه المركزي:** جدول الوصول في المركز
يُطابَق بالبريد. و`state` قيمتها `granted` أو `revoked` حصراً — وما عداهما
يردّ عليه المركز `invalid_state`.

## التجديد

عند انتهاء الجلسة المحلية **يُطلب رمز جديد من المركز**. الجلسة لا تجدّد نفسها، وإلا بقي الموقوف مركزياً يدخل حتى انتهاء كوكيه. وهذا سلوك الوسيط تلقائياً ولا يحتاج ضبطاً.

---

## شكل الردّ يتبع طبيعة الطلب

الرمز يعيش خمس عشرة دقيقة، فالمنع ليس حدثاً نادراً: لوحةٌ مفتوحة أطول من ذلك تبلغه في كل مرة. والوسيط يفرّق بين حالين، وبطبيعة الطلب لا ببادئة مساره:

| الطلب | لا جلسة | ممنوع (موقوف أو غير عضو) |
|---|---|---|
| تنقّل يعرض صفحة | `302` إلى `‎{issuer}/go/{platformId}` | `302` إلى `‎/denied?r=…` |
| نداء برمجي (`fetch`) | `401` + `{ ok:false, error:"unauthorized", login }` | `403` + `{ ok:false, error:"access_denied", reason, denied }` |

**ولماذا لا تُجزئ البادئة.** رابط تنزيلٍ تحت `‎/api/` تنقّلٌ من المستخدم، وردُّ `JSON` عليه يعرض عليه نصّاً خاماً مكان أن يعيده إلى الدخول. والعكس يقع كذلك: نداءُ `fetch` إلى مسارٍ خارج البادئات يأخذ تحويلةً لا تنفعه — تحويلة «لا جلسة» تقصد نطاق المركز فيسقط الطلب بخطأ شبكة بلا `CORS`، وتحويلة «ممنوع» داخليةٌ **يتبعها `fetch` بنجاح** فيستقبل صفحةً نصّاً ويسقط تحليل `JSON` بخطأ لا صلة له بالسبب.

فالحكم بـ`Sec-Fetch-Mode` أوّلاً — يقولها المتصفّح صراحةً — ثم بـ`Accept`. و`apiPrefixes` تبقى في الإعداد لعميلٍ لا يرسل الترويستين معاً، وهي **آخر** ما يُسأل لا أوّله.

والسبب يبقى رمزاً لا جملة في الحالين: ترجمته إلى المصطلح المسجَّل في `naf-terms.md` عمل صفحة `‎/denied` وحدها.

## عقد السلك مع المركز

أسماء الحقول هي أسماء `naf-id` حرفياً. والمركز يفحص أنواعها ويردّ
`invalid_body` على أي اختلاف — فاسمٌ بصيغة أخرى يُسقط كل دخول في المنصة،
ويفشل فشلاً لا يفرّق بينه وبين سرّ خاطئ.

**المبادلة** — خادماً لخادم، ولا ترويسات `CORS` على هذا المسار عمداً:

```
POST {AUTH_ISSUER}/api/token
  { "platformId": "...", "secret": "...", "code": "...", "state": "..." }
  ← { "token", "tokenType": "Bearer", "expiresIn": 900, "next" }
```

رمز العبور عمره **ستون ثانية ويُستهلك مرة واحدة**. فإعادة استعماله تفشل
حتماً، ولا يُعاد بها المحاولة.

**التبليغ العكسي** — حين تُوقف المنصة عضواً في إعداداتها المحلية:

```
POST {AUTH_ISSUER}/api/internal/access
  { "platformId", "secret", "email", "state": "granted"|"revoked", "reason"? }
```

والعضو يُعرَّف **بالبريد** لا بالمعرّف المركزي. والمنصة تبلّغ عن نفسها لا عن
غيرها: المركز يشتقّ المنصة من سرّها لا من جسم الطلب.

**التحويل إلى الباب:**

```
GET {AUTH_ISSUER}/go/{PLATFORM_ID}?next=/path
```

و`‎/go/:id` **يتجاهل أي `state` يصله** ويولّد واحدة من عنده. فحالةٌ من طرف
المنصة لا تعود إليها أبداً، ومطابقتها عند الاستقبال تفشل حتماً.

## الاحترازات الأمنية المطبَّقة

| # | الاحتراز | الموضع |
|---|---|---|
| ١ | `next` يُقبل فقط إذا بدأ بشرطة مائلة واحدة، ولم يبدأ بشرطتين، ولم يحوِ نقطتين رأسيتين — وإلا فالجذر | `safeNext` |
| ٢ | `state` يُعاد إلى المركز كما وصل، والمركز يطابقه برمز العبور ويرفض عند الاختلاف | `exchangeCode` |
| ٣ | السرّ عبر `wrangler secret` حصراً، ولا يدخل رسالة خطأ ولا سجلّاً | `exchangeCode` |
| ٤ | التوقيع و `iss` و `aud` و `exp` — الأربعة معاً، وفارق الساعة لا يتجاوز ٦٠ ثانية | `verifyToken` |
| ٥ | كاش المفاتيح ٥ دقائق، **مع إعادة جلب فورية عند `kid` غير معروف** | `verifyToken` |
| ٥أ | **التحقق يقع في كل طلب محمي لا عند الاستقبال وحده**، وعمر الجلسة لا يتجاوز عمر الرمز | `authenticate` |
| ٦ | الكوكي `HttpOnly` و `Secure` و `SameSite=Lax` و `Path=/` وبلا `Domain` مشترك | `sessionCookie` |
| ٧ | معرّف الجلسة عشوائي بالكامل، لا يُشتقّ من `sub` | `newSessionId` |
| ٨ | صفحة الرفض تعرض السبب فقط، بلا تفاصيل تقنية | رموز الأسباب أعلاه |
| ٩ | كل تغيير بعد الوسم يستلزم وسماً جديداً وتحديثاً واعياً في كل منصة | `CHANGELOG.md` |

**وتنقية `next` تقع مرتين:** عند إرسالها إلى المركز، وعند العودة منه — سواء
جاءت في الرابط أو في ردّ المبادلة. وأن المركز فحصها لا يُغني: هذا الطرف من
يضعها في ترويسة `Location`، وقد يفكّ ترميزها مرة أخرى فتصير شيئاً آخر. ولذلك
يُفكّ الترميز حتى يستقرّ ويُفحص الشكلان: كما وصل وكما سيؤول.

**زيادتان على تنقية `next`، كلتاهما أضيق لا أوسع:** رفض الشرطة العكسية — المتصفح يطويها إلى مائلة فيصير `/\evil.sa` هو `//evil.sa` ويتجاوز شرط «لم يبدأ بشرطتين» حرفياً — ورفض محارف التحكّم، لأنها تُحذف من ترويسة `Location` فيتغيّر المسار بعد تنقيته.

## الاستقرار والتوافق

`v2.0.0` هو العقد الثابت الحالي. و`v1.0.0` **لا يعمل**: كانت أسماء حقوله
مخالفةً لما يقرؤه المركز، وكان يولّد حالةً عابرة لا يعيدها المركز، ويتحقّق من
الرمز عند الاستقبال وحده — فكل دخول يفشل، وكل جلسة تعمّر بعد رمزها. لا تُثبَّت
منصةٌ عليه.

ما يلي سطح `v2.0.0` العام، ولا يتغيّر إلا برقم إصدار رئيسي جديد:

| السطح | ما يشمله |
|---|---|
| الإعداد | `createConfig(env, overrides)` وحقول `AuthConfig` |
| الوسيط | `authenticate` و `pagesMiddleware` و `honoMiddleware` و `isPublicPath` |
| الاستقبال | `handleCallback` و `pagesCallback` و `onClaims` و `reportAccessChange` |
| التحقق | `verifyToken` |
| الأعضاء | `getMember` و `upsertMember` و `touchMember` ومخطّط الأعمدة |
| التنقية | `safeNext` وتوابع الكوكيز والمعرّفات |
| المتغيّرات | أسماء `PLATFORM_ID` و `AUTH_ISSUER` و `MEMBERS_*` و `DEFAULT_ROLE` |
| رموز الرفض | `inactive` و `not_member` و `bad_state` و `auth_failed` |
| عقد السلك | أسماء حقول `‎/api/token` و `‎/api/internal/access` أعلاه |

**والوسم عقد.** متى استهلكت منصة واحدة إصداراً، جُمّد محتواه: أي تغيير بعده يستلزم رقماً جديداً. وإعادة وسم إصدار مستهلَك تعطي منصتين محتوى مختلفاً تحت اسم واحد — وهو أسوأ أنواع الفشل لأنه صامت.
